## 任务描述

### 可验证结果

地图加载由应用层唯一、显式且可验证的状态流驱动，完整覆盖下载、解析、校验、节点编译、路径编译、场景创建、淡入、就绪和错误；并发会话、取消、非法转换和过期结果都有确定行为。

### 输入

- SPEC §5.1、§5.3、§5.4、§10、§13.1、§16.3 中的分层依赖、状态联合、进度、不变量、错误码和会话生命周期要求。
- TASK-001 至 TASK-005 已交付的严格数据边界和完整可转移场景编译包契约。
- 任务开始时仓库内已有的状态机、会话控制和测试实现；必须审计展示层是否直接驱动内部状态以及应用层是否反向依赖基础设施具体实现。

### 输出

- 封闭的加载状态联合：五个后台加载阶段、两个场景准备阶段、ready 和统一 error，准备与就绪状态携带同一完整渲染数据包。
- 严格单向状态转换和 0～1 单调进度映射：下载 0～30%、解析离散 30%、校验 30～40%、节点 40～55%、路径 55～90%、场景创建 90～98%、淡入 98～100%。
- 六个稳定错误码及其发生阶段、简短中文说明和结构化详情契约。
- 每次加载唯一 requestId、同一时间单一有效会话、取消后冻结、旧会话消息隔离以及重复挂载安全的应用层生命周期能力。
- 面向展示与基础设施的窄应用边界，使状态转换只由应用层用例采纳，其他层不能绕过状态规则直接修改会话内部状态。
- 覆盖合法全流程、非法跃迁、进度回退、取消、会话取代、过期消息、错误终态和订阅清理的 Node 环境自动化验证。

### 实现约束

- 状态转换规则必须是可重复验证的纯逻辑；会话控制可以管理订阅和 requestId，但不得依赖 React、Three.js、Worker 或 DOM。
- `progress` 始终有限、位于 0～1 且单调不下降；JSON 解析不得伪造连续进度，ready/error 为终态。
- 同一时间只允许一个有效会话；新会话必须使旧 requestId 立即失效，取消或卸载后任何旧进度、成功和失败都不得覆盖当前状态。
- 应用层只能依赖领域契约及由应用边界拥有的协作契约，不得直接依赖基础设施具体实现；基础设施可依赖并实现应用所需边界。
- 展示层只能提交“场景资源已完成步骤、首帧成功、淡入完成或创建失败”等外部事实，由应用层决定状态转换，不得持有并任意调用内部会话控制对象。
- 不增加 idle、重试、fallback、deprecated、旧状态兼容或隐式全局 store；错误后不自动重试。

### 验证方式

- 执行 `pnpm test`，预期状态机、会话、错误映射及 TASK-001 至 TASK-005 回归测试全部通过。
- 执行 `pnpm lint` 与 `pnpm build`，预期无类型、依赖方向、lint 或构建错误。
- 正常路径：按七个活跃阶段顺序提交真实阶段内进度、挂载完整数据包并完成；预期状态严格前进、总进度单调并最终 ready。
- 关键异常路径：提交跨阶段、回退进度、终态后写入、无数据包进入场景创建、无首帧事实完成淡入；预期转换被拒绝且当前状态不变。
- 会话路径：快速开始两个会话，随后交错提交旧会话进度、成功和失败，再取消当前会话；预期只有最新未取消 requestId 可更新，取消后不能进入 ready。
- 错误路径：在对应阶段分别提交六类稳定错误；预期进入统一 error，保留错误码、实际阶段、中文说明和详情，且无自动重试。验证不启动浏览器。

### 完成标准

- 显式状态流、错误契约、唯一会话和应用层边界均已实现并由自动化测试证明。
- `pnpm test`、`pnpm lint`、`pnpm build` 全部通过，TASK-001 至 TASK-005 的行为没有被破坏。
- 依赖方向与 SPEC 一致，不存在 application→infrastructure 具体实现依赖、展示层直接改状态、全局可变会话或重复状态逻辑。
- 与本任务相关的改动可形成单一独立 Git checkpoint，不混入 Worker 下载或场景展示实现。
- 代码库处于一致、可运行、可验证状态，可以安全进入 TASK-007。

回退本 TASK 的 Git checkpoint 只移除或还原显式状态流、会话隔离、错误契约和应用边界；TASK-001 至 TASK-005 的纯数据与几何编译结果保持完整，不受加载编排回退影响。
