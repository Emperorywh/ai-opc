## 任务描述

### 可验证结果

应用层以唯一、可判别的状态机编排 worker 请求、场景模型提交、Three 资源准备和本地字体预加载。只有当前请求能够从 `idle` 经 `loading`、`preparing` 进入 `ready`；任一阶段失败进入带稳定上下文的 `error`，重新加载、卸载和 StrictMode 重复生命周期不会提交过期结果或泄漏已创建资源。

### 输入

- SPEC 第 4.2～4.3、13、14.1、15.3 节规定的加载状态、请求竞态、资源所有权、错误可观测性和生命周期不变量。
- TASK-013 交付的 worker 消息协议、请求 ID、阶段消息、成功场景模型和结构化失败结果。
- TASK-014 交付的 Three 资源创建、整体拒绝和幂等释放边界。
- TASK-015 交付的字形门禁、字体预加载及字体就绪/失败信号。
- 用户确认的本地运行边界；WebGL 可用性、context lost/restore 和可见错误 overlay 的浏览器集成由后续 TASK 交付。

### 输出

- `idle`、`loading`、`preparing`、`ready`、`error` 五种互斥状态及其允许事件、稳定阶段名和只读上下文。
- 单调递增请求 ID、当前请求判定、worker 创建/终止和异步结果提交的 application 编排契约。
- 场景模型、资源准备和字体就绪三者的明确门禁；缺少任一成功结果时不得进入 `ready`。
- 重新加载、过期 worker 结果、过期字体回调、资源创建失败、卸载和 StrictMode 重复初始化的统一清理行为。
- 可供后续 UI 直接投影的结构化错误状态，包含错误码、阶段、简体中文消息和可用上下文，但不在本任务创建具体 overlay。
- 覆盖正常状态序列、并发竞态、各阶段错误、重试和 20 次挂载/卸载的自动化测试。

### 实现约束

- 所有状态转换只能由 application 层的单一 reducer 完成；组件不得分别维护“正在加载”“模型已到达”“字体已加载”或“资源已创建”等隐式布尔状态。
- 每次开始或重新加载都分配严格单调递增的请求 ID；只有与当前 ID 相同的 worker 消息、资源结果和字体回调可以改变状态。
- `loading` 只表示当前 worker 正在请求样本；解析、校验、几何构建、资源准备和字体预加载均处于 `preparing`；三项门禁全部满足后才进入 `ready`。
- 过期成功结果不得进入资源适配或状态；其 ArrayBuffer 引用必须立即脱离 application 状态并可被回收。过期失败和字体回调同样不得覆盖当前请求。
- 新请求、卸载或 HMR 清理必须终止旧 worker，并释放旧请求已经创建的全部 Three 资源；清理在 StrictMode 下必须幂等。
- 任一当前阶段失败都必须释放本次部分资源并进入单一 `error` 状态；错误状态不得携带可展示的部分地图资源。
- 重试从新的请求 ID 重新进入 `loading`，不得复用失败请求的 worker、可变 SceneModel、资源或错误对象。
- application 层只编排已定义端口和不可变契约，不解析 JSON、不生成几何、不创建具体 Three 资源、不预加载之外创建文字，也不维护相机或标签可见状态。
- 本任务不实现 WebGL DOM 事件绑定、context restore、R3F 场景和错误 overlay；后续集成必须通过本状态机事件扩展，不得建立第二套加载状态。
- 新增或修改的代码必须使用多行简体中文注释说明状态转换、requestId 竞态、ready 门禁与清理不变量；不得主动格式化无关代码。

### 验证方式

在 `C:\code\ai-opc\agv-map-3d` 执行：

```powershell
npm run lint
npm test -- --run
npm run build
```

- 正常路径：以可控 worker、资源和字体端口启动请求，预期状态严格经历 `idle → loading → preparing → ready`，且 `ready` 同时持有当前 SceneModel 和完整资源引用并记录字体已就绪。
- 正常路径：改变资源和字体成功顺序，预期在最后一个门禁完成前始终保持 `preparing`，完成后只提交一次 `ready`。
- 关键异常路径：连续发起两个请求，让旧请求在新请求之后返回成功、失败或字体回调；预期旧结果全部被忽略、缓冲区不进入状态、旧 worker 被终止且当前状态不被覆盖。
- 关键异常路径：分别模拟 worker 请求/解析/数据错误、资源创建中途失败和字体缺字/加载失败，预期进入包含相应稳定错误码和阶段的 `error`，并释放部分资源且不保留部分地图。
- 关键异常路径：连续执行 20 次启动、ready、卸载及 StrictMode 风格的重复清理，预期 worker、资源登记和订阅计数不单调增长；随后重试使用更大的请求 ID 并可正常 ready。
- 预期结果：三个命令退出码均为 0，状态序列、门禁、竞态、错误、重试和生命周期断言全部通过；验证不启动浏览器。

### 完成标准

- application 已成为加载状态与请求竞态的唯一所有者，正常路径和所有关键失败路径均有确定状态结果。
- 相关 lint、测试和构建全部通过，此前 TASK 的 worker、场景模型、资源和字体契约未被破坏。
- 当前请求门禁、过期结果丢弃、worker 终止、资源释放、重试和 StrictMode 幂等行为全部通过自动化验证。
- 没有组件级重复状态、部分地图、旧请求覆盖、隐藏缓存、跨层业务计算或错误 fallback。
- 当前状态可建立仅覆盖 `agv-map-3d` 子目录的独立 Git checkpoint，并安全进入 TASK-017。
