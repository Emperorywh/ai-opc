# 中国三维地形地图修复规格说明

## 1. 文档目的

本文档定义中国三维地形地图完成 `TASK-001` 至 `TASK-013` 后必须达到的统一产品效果、领域语义、状态不变量、架构边界和验收基线。

本文档冻结“系统必须交付什么结果”，不规定需要修改或创建的具体文件、类、函数、组件、测试目录或内部实现模式。Coding Agent 必须在执行每个 TASK 前检查当时的实际代码、数据流和状态流，再决定符合本规格的实现位置与技术细节。

本文档是现有已确认外部契约、政治合规要求、安全要求、部署约束和全局架构决策之下的修复规格，不替代这些上位约束。单个 TASK 可以进一步收紧局部结果，但不得削弱本文档的不变量。

## 2. 最终目标

全部任务完成后，系统必须成为可在 1080p 和 4K 大屏上稳定运行的、离线的、以真实中国地貌为主体的三维地理展示页面，而不是仅接通数据和图层的工程演示。

最终页面必须同时满足以下结果：

- 默认全国视角能直接辨认青藏高原、主要盆地、东部平原、雪线和海拔梯度，三维体积感来自真实高程而不是颜色、边界或局部造型补丁。
- 陆地、真实海域、水下大陆架、行政边界、政治要素、标签和地点光点具有稳定、正确的空间与深度关系。
- 海面只覆盖真实海域，水面动态细微可信，不在陆地上产生条纹、闪烁或透明着色。
- 行政区边界、争议区修正、所属判断和人工核对使用同一份最终政治几何事实。
- 资产加载、场景准备、入场、交互、运行时丢失与恢复均具有显式、可诊断且不可矛盾的状态。
- 悬停命中用户实际看到的位移地形，并只输出一个稳定的省级焦点。
- 生产页面具有明确的视觉层级、可读的图例与南海附图、完整的合规信息，不呈现开发调试工具观感。
- 目标独显设备上的生产默认场景在 1080p 和 4K 动态操作中持续达到 60fps，并有可复核的测量记录。

## 3. 产品范围

### 3.1 范围内

- 离线高程、行政区、政治要素、地点、字体、来源注册表及相关元数据的加载与校验。
- 真实米制高程、渲染显示空间、垂直夸张、相机和深度精度的一致性。
- 地形、海域、水下大陆架、边界、政治线点、地点光点和固定地理标签的三维展示。
- 省级悬停、标签遮挡、单一焦点和无焦点恢复。
- 加载、派生准备、入场、运行、WebGL context 丢失与恢复、resize 和错误反馈。
- 海拔图例、南海诸岛附图、加载/恢复反馈和合规角标。
- 1080p、4K、长期运行和资源生命周期的性能与稳定性验收。

### 3.2 范围外

- click、下钻、飞焦、业务 tooltip、业务数据接入和业务仪表盘。
- 移动端布局、响应式业务页面和多终端适配。
- 在线地图、在线字体、在线纹理、运行时流式数据或其他外网 fallback。
- 卫星影像、天空盒、装饰性图表、实时标签碰撞和与地理展示无关的视觉模块。
- 自动低清、旧资产兼容、灰度、deprecated 路径或 legacy 数据迁移。
- 正式地图审图、公开发布或对外宣称已经取得审图号。
- 生产页面中的垂直夸张切换、网格分段选择和其他开发调试控件。

## 4. 术语与统一语义

### 4.1 真实海拔

真实海拔是从统一离线高程资产及元数据解码得到的米制值。它未应用垂直显示夸张，是地表色阶、海拔图例、海陆分类、标签贴地和所有领域查询的事实依据。

合法负高程、`0m` 海平面和正高程必须可区分。数据不可用、编码不匹配或查询失败不得伪装成 `0m`。

### 4.2 显示高度

显示高度是由真实海拔、统一渲染空间契约和垂直夸张共同推导的渲染结果。显示高度只服务三维呈现，不得回写真实海拔、地理资产或海陆分类。

### 4.3 垂直夸张

垂直夸张记为 `k`，合法范围为 `1.5–3.0`，默认值为 `2.0`。改变 `k` 只能连续改变垂直起伏强度，不得改变经纬度、投影位置、真实海拔、色阶、海岸线、行政区归属或资产缓存。

### 4.4 海平面与海域

统一海平面为真实海拔 `0m`。海面只允许作用于真实海拔低于海平面的区域；真实海拔大于等于 `0m` 的陆地片元不得受到海面颜色、透明度或动态波动影响。

### 4.5 最终行政区几何

最终行政区几何是基础 34 个省级行政区边界与全部必需、可追溯政治修正确定性合成后的唯一运行时事实。贴地边界、悬停所属判断和相关核对不得绕过该事实直接消费未经修正的基础几何。

### 4.6 必需资产与派生结果

必需资产是最终页面不可缺少的外部静态输入。派生结果是基于已加载资产计算得到的地形、边界、政治要素、标签、附图、图例和合规呈现所需结果。二者必须分别建模，不得用“文件已下载”替代“场景已可完整呈现”。

### 4.7 完整可交互

完整可交互表示所有必需资产已加载、全部必需派生结果已准备、入场已完成且运行时正常。缺少任一必需图层、字体、来源、政治修正或合规内容时，不得进入该状态。

## 5. 全局业务规则与状态不变量

### 5.1 单一事实源

- 同一页面生命周期内，同一高程资产与元数据只能形成一个活动的 CPU 高程查询所有者。
- CPU 与 GPU 可以使用不同表示，但必须共享同一编码、元数据和真实米制语义。
- 地形、边界、政治要素、标签、遮挡、海陆判断与悬停不得各自解码或维护第二份高程事实。
- 海拔色阶与海拔图例必须共享唯一配置。
- 主图与南海附图必须共享政治坐标、名称、投影及最终政治事实，不得形成双轨数据。

### 5.2 空间一致性

- 地形、边界、政治线点、标签、地点光点、相机、遮挡和悬停必须遵守同一地理投影与渲染空间语义。
- 同一地理点的所有三维表示在任意合法 `k`、相机状态和目标分辨率下保持对齐。
- 显示变换必须位于明确的坐标或渲染适配边界，不能散落成图层私有缩放和偏移。
- 不允许按山脉、盆地、省份、标签或特定相机角度加入局部修正来制造正确观感。

### 5.3 海陆与深度关系

- 海陆分类只由真实海拔和统一海平面决定，不得由显示高度、地表颜色或行政区几何推断。
- 低海拔陆地必须稳定遮挡海面，不能依赖深度缓冲偶然舍入。
- 水下负高程地形必须保留在海面之后并可通过半透明水体辨识。
- 贴地边界和政治线只允许使用统一、可解释且受预算约束的深度关系，不能永久穿透前方地形。
- 合法相机范围内不得出现海陆交替覆盖、规则扫描线、z-fighting、边界穿插或深度量化条带。

### 5.4 错误与失败

- 必需资产或派生结果失败必须进入可诊断错误状态，包含可定位的失败对象和原因。
- 失败不得被吞掉、只写入控制台、转换为空图层、伪装成成功或自动使用旧结果覆盖。
- 禁止平地、全图海面、低清资产、旧数据、在线资源或平面拾取等隐藏 fallback。
- 政治修正缺失、重复、冲突或来源不可追溯时，完整场景必须保持不可验收状态。

### 5.5 交互

- 同一时刻最多存在一个以稳定行政区 ID 表达的省级悬停焦点。
- 指针命中必须对应用户可见的位移地形表面，而不是 `y=0` 平面、海平面或包围盒。
- 海域、地图外和无命中必须恢复无焦点；快速跨省不得残留多个高亮。
- click 不产生任何状态转换。

### 5.6 生命周期

- 重复挂载、StrictMode 重挂载、配置切换、context 丢失/恢复和连续 resize 不得造成 CPU 高程重复解码或外部资产重复请求。
- GPU 资源必须具有明确所有者，能够按职责复用、恢复和释放。
- context 恢复只重建丢失的 GPU 表示，继续复用有效 CPU 资产和领域派生结果。
- resize 只能具有一个实际提交所有者，最终渲染尺寸必须等于最后一个有效输入。
- 卸载后监听器、时钟、定时器、几何、材质、纹理及大数组引用必须可释放。

## 6. 运行状态规格

系统必须采用可推导的显式状态，禁止由多个互不约束的布尔值组合出矛盾状态。

| 状态 | 进入条件 | 允许的后续状态 | 是否允许入场 | 是否允许交互 |
| --- | --- | --- | --- | --- |
| 资产加载中 | 页面启动且必需资产尚未全部完成 | 场景准备中、错误 | 否 | 否 |
| 场景准备中 | 所有必需资产已就绪 | 入场中、错误 | 否 | 否 |
| 入场中 | 所有必需派生结果已就绪 | 完整可交互、错误 | 是 | 否 |
| 完整可交互 | 入场完成且运行时正常 | 恢复中、错误 | 已完成 | 是 |
| 恢复中 | GPU context 丢失后开始恢复 | 完整可交互、错误 | 否 | 否 |
| 错误 | 任一必需输入、派生结果或恢复失败 | 由显式重新初始化进入资产加载中 | 否 | 否 |

附加约束：

- 加载进度只能由已登记必需资产的真实完成情况推导，不得由计时器、固定总数或装饰资源伪造。
- 第一个失败原因及对应对象必须可定位；失败状态不得自动跳回成功。
- 同一资产版本和配置组合下，同一派生工作最多执行一次；配置变化只允许重算受影响结果。
- 运行时暂停、恢复和水面动画必须服从同一生命周期与帧循环。

## 7. 功能规格

### FR-001 唯一高程资源

系统必须只创建一份可查询的 CPU 高程表示，并供全部领域消费者只读共享。垂直夸张切换不得触发重新解码；最后一个所有者释放后资源必须可回收且不可继续查询。

### FR-002 全国尺度真实地形

默认完整中国视角、`k=2.0` 时，青藏高原必须明显高于东部平原，塔里木盆地和四川盆地必须相对周边山地明显下凹，雪线和主要高程梯度可直接观察。地貌辨识必须来自真实三维位移，不得通过色彩或缩小地图范围伪造。

### FR-003 全相机范围深度稳定

默认、最近、最远和接近最大合法俯仰角的全部相机状态必须满足统一深度预算。相机裁剪面应由地图包围盒、最大显示高度和合法操作范围推导，并在 resize 与 context 恢复后保持一致。

### FR-004 真实海域覆盖

海面必须只覆盖真实海域。海岸临界区域、低地、岛屿和沿海在全部合法 `k` 与相机状态下必须稳定；高程或海域判定不可用时，海面层必须显式失败。

### FR-005 可信动态海面

水面必须呈现细微、连续、非规则扫描线式的动态微波，并通过视角、光照及真实负高程表现大陆架层次。水面不得遮蔽陆地、十段线、岛礁点、沿海省界或低地标签，也不得引入独立动画时钟和逐帧大分配。

### FR-006 完整资产加载

加载闭环必须至少覆盖高程、行政区、政治数据、地点、实际离线字体、字体清单、来源注册表及最终页面其他必需静态输入。所有必需资产就绪前不得进入场景准备完成或入场状态。

### FR-007 完整场景准备

地形、贴地省界、政治线点、标签与字体覆盖、南海附图、海拔图例和合规角标必须全部报告派生准备结果。任何必需层失败都必须阻止入场和交互，并通过统一错误反馈呈现。

### FR-008 最终政治几何

藏南、阿克赛钦及政治完整性清单要求的修正必须确定性作用于最终行政区边界和所属判断。修正必须恰好存在、来源可追溯、无冲突，并经过机器校验和人工公开标准地图基准核对；自动化和人工核对均不能替代正式审图。

### FR-009 真实地形悬停

系统必须从屏幕指针确定可见地形交点，再反查经纬度和最终行政区稳定 ID。高原、盆地、斜视、缩放、全部合法 `k`、海岸、内环、岛屿和相邻边界必须具有确定结果。

### FR-010 GPU 资源生命周期

地形、海面、边界、政治线点、标签和地点光点使用的 GPU 资源必须可审计地创建、共享、恢复和释放。静态几何与材质不得创建无意义副本；恢复失败必须进入统一错误状态，不得空白死循环、自动刷新或降级。

### FR-011 主图视觉层级

默认画面必须首先读到真实地势体积和高程色阶，其次读到省级边界与十段线，最后读到省名、省会光点和岛礁标注。正常边界应清楚但克制，只有悬停省份获得显著焦点。

34 个省级行政区名称、省会光点、港澳台及必需岛礁名称必须完整、清楚且稳定。标签遮挡、悬停、入场和恢复状态必须按统一优先级合成，不得互相覆盖或永久穿透地形。

### FR-012 外围 UI 与南海附图

1080p 和 4K 下，海拔图例、南海附图、加载/恢复反馈和合规角标必须分区明确、文字可读、不互相重叠且不遮挡主图核心区域。

南海附图必须呈现可辨认的十段线、台湾东侧段、必需岛礁点和名称，并具有足够地理上下文。合规角标必须完整显示审图号占位、数据来源、非官方状态和不得正式发布免责声明，且不得把占位符伪装为已获批号码。

### FR-013 最终性能与回归

生产默认配置必须在目标独显设备的 1080p 和 4K 环境中，以真实渲染尺寸和生产 DPR 进行动态测量，持续达到 60fps。测量必须覆盖旋转、缩放、平移、连续悬停、标签密集区、南海区域、context 恢复、连续 resize 和长时间运行，不得只测静止空闲帧。

若目标未达到，规格保持未验收状态，直至基于真实瓶颈完成合法优化并重新测量。不得通过隐藏政治要素、删除标签、降低实际分辨率、自动低清或伪造记录完成验收。

## 8. 架构边界与依赖方向

系统必须维持以下单向依赖关系：

1. 离线资产与元数据提供不可变输入。
2. 资产加载层负责请求、校验、进度和加载错误，不依赖具体 3D 场景或 DOM UI。
3. 领域准备层负责高程、最终行政区几何、政治要素、标签锚点及其他可复用事实，不依赖渲染框架、页面组件、悬停状态或 UI。
4. 坐标与渲染适配层把真实米制领域事实转换为统一显示空间，不得反向修改领域数据。
5. 渲染层只消费领域事实和显示契约，管理 GPU 表示，但不得成为高程、政治边界或海陆分类的事实源。
6. 交互层可以消费相机、可见地形和最终行政区几何，只输出稳定业务状态，不得修改资产、派生结果或渲染对象。
7. 页面编排层只组合加载、准备、入场、运行和错误状态，不复制领域计算。
8. DOM overlay 只消费状态和领域配置，不得反向控制或重建三维事实。

任何必要重构都必须服务于上述边界。禁止通过全局可变单例、巨型场景组件、组件内私自请求、重复包装、复制大数组、双轨几何或跨层读写完成需求。

## 9. 视觉规格

### 9.1 主图

- 深色科技风保持克制，地形体积和真实高程色阶是第一视觉主体。
- 海面是辅助环境层，其动态强度不得抢夺陆地和政治边界焦点。
- 正常省界不能成为全屏最高对比度元素；悬停态必须显著但不破坏其他省界可读性。
- 标签和光点必须支持地理阅读，不能替代地貌，也不能以点状噪声覆盖地形。
- 雾、光照和透明关系不得掩盖高原、盆地、低地、岛屿或大陆架。

### 9.2 外围信息

- 页面外围只允许海拔图例、南海附图、加载/恢复反馈和合规角标。
- 海拔图例必须完整呈现与地表共享的六个关键刻度及单位语义。
- 长文本不得产生破碎换行、来源与免责声明混淆或不可读缩放。
- 外围布局不得遮挡新疆、西藏、东部沿海、台湾或主图南海政治要素。
- 生产页面不得显示垂直夸张、网格分段或其他开发调试入口。

## 10. 数据与合规规格

- 运行时必须完全离线，生产页面不得访问外网或在失败后尝试远程资源。
- 所有政治补充、争议区修正和项目维护数据必须保留来源边界，不得伪装成第三方官方数据。
- 机器校验必须覆盖资产存在性、编码、范围、稳定标识、修正完整性、重复与冲突。
- 最终政治几何必须由人工对照可追溯公开标准地图基准核对，并记录核对人、日期、基准和未决项。
- 存在未决政治项时不得完成相关 TASK，也不得公开部署。
- 页面必须持续声明非官方、仅内部展示、未取得审图号且不得正式发布；后续视觉优化和性能优化不得省略或弱化该信息。

## 11. 性能与可靠性规格

### 11.1 性能

- 最终记录必须包含 GPU、浏览器、分辨率、DPR、地形网格档位、采样时长、fps 分布、内存或显存可观察指标、draw call 和完整操作路径。
- 生产默认网格精度、34 个省级标签、政治必需要素、南海附图和合规 UI 不得为帧率被删除。
- DPR、网格档位和检查降频必须是显式配置；高配档不得自动启用。
- 动画帧只更新必要的小型状态，不得逐帧创建对象、大数组、材质、几何或纹理。

### 11.2 可靠性

- 长时间动态运行不得出现持续内存增长、资源数量增长、状态漂移或交互退化。
- context 可恢复时必须恢复一致画面、交互和 overlay；不可恢复时必须显示可诊断错误。
- 连续 resize 后不得存在重复提交、过期尺寸覆盖或卸载后继续响应。
- 重复挂载和 StrictMode 下的加载、派生计算、监听器、时钟和资源数量必须稳定。

## 12. 验收规格

### 12.1 自动化验收

每个 TASK 必须包含产生对应结果所需的测试、必要重构和相关说明。最终至少需要证明：

- 高程只有一次 CPU 解码和一个活动查询所有者，全部消费者查询结果一致。
- `k=1.5/2.0/3.0` 只改变显示高度，其他领域事实保持不变。
- 关键高地、盆地、平原、海平面和水下样本的空间与深度顺序正确。
- 海面覆盖集合不随 `k` 或相机变化，且高程失效不会产生全图海面。
- 必需资产和派生层的成功、乱序、失败、重挂载及配置变化均具有确定状态。
- 最终政治几何的必需修正、冲突和消费路径可验证。
- 悬停覆盖高差、相机、海域、边界、岛屿和无命中状态。
- GPU 资源、监听器、时钟、context 恢复和 resize 的数量与所有权稳定。
- 34 个省级名称与省会光点、港澳台、十段线和必需岛礁要素未被删除。
- 生产 UI 不包含开发调试控件，图例、附图、来源和免责声明完整。

所有任务必须通过项目实际存在且与变更相关的测试、资产校验、lint 和生产构建命令。TASK 中列明的命令是当前验收入口；若执行时脚本发生合法架构调整，必须提供等价且可复核的验证证据，不得跳过验证目标。

### 12.2 人工视觉与交互验收

人工验收至少覆盖：

- 1080p 与 4K、默认/最近/最远缩放、低俯角及持续相机旋转。
- 青藏高原、塔里木盆地、四川盆地、东部平原、海南、台湾、沿海岛屿和大陆架。
- 海岸低地、边界密集区、标签密集区、南海附图和政治必需要素。
- 快速跨省悬停、海域与地图外恢复、context 丢失/恢复和连续 resize。
- 加载失败、派生失败和恢复失败的可诊断反馈及交互锁。

Coding Agent 不得自动启动浏览器；页面视觉、目标硬件性能和需人工判断的政治核对由用户手动执行并记录。

### 12.3 最终完成标准

只有同时满足以下条件，整个修复规格才算完成：

- `TASK-001` 至 `TASK-013` 已严格按顺序完成，每个 TASK 都有独立、可回退的 Git checkpoint。
- 全部功能、数据、状态、视觉、交互、资源所有权和架构不变量均有自动化或等价证据。
- 1080p 与 4K 的人工视觉、交互和性能验收通过。
- 目标独显设备上的生产默认场景持续达到 60fps，长时间运行无资源持续增长。
- 政治数据机器校验和人工核对通过，且页面仍明确保持非官方、未审图、不得正式发布状态。
- 不存在隐藏 fallback、重复事实源、跨层耦合、临时补丁、legacy 兼容或未记录例外。

## 14. 执行、变更与回退规则

- TASK 必须严格按数字顺序线性执行；只有前一 TASK 完成并建立 Git checkpoint 后才能开始下一 TASK。
- 每个 TASK 开始前必须重新检查实际代码、架构、数据流和状态流，不得照搬文档中不存在的内部结构假设。
- 每个 checkpoint 必须只包含当前可验证结果、必要重构、测试和相关说明，并保持代码库一致、可运行、可验证。
- 回退当前 TASK 时必须保留此前所有 TASK 的已验收结果；无法隔离回退说明任务边界或实现耦合不合格。
- 若实现发现本规格与已确认上位契约冲突，必须停止冲突部分并先修正文档，不得在代码中创建例外或兼容分支。
- 若需要改变本文档冻结的业务规则、状态不变量、模块边界或完成标准，必须先更新规格和全部受影响且尚未执行的 TASK，再继续编码。
- 新增或修改的代码必须使用多行简体中文注释解释关键领域语义、资源所有权、状态转换和架构边界，不得主动格式化无关代码。
- 禁止临时 patch、copy-paste、巨型函数或组件、隐式状态、魔法逻辑、重复逻辑和跨层耦合。
